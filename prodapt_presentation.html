Executive Summary

The Prodapt AI Operations Center is an intelligent multi-agent system designed to automate and orchestrate customer support operations for a mid-size telecom provider. This system integrates five complementary AI frameworks to create a seamless, policy-compliant, and data-driven customer service solution.

Problem Statement

Current operations are fragmented across multiple systems with average handle times of 15-25 minutes for complex inquiries. Knowledge silos prevent consistent policy interpretation, and wrong-team routing causes customer frustration.

Proposed Solution

A unified AI orchestration platform that routes requests intelligently to specialized workers, leveraging LangGraph supervision, LlamaIndex retrieval, ADK agents, and CrewAI communication specialists.

Key Capabilities

  • Policy-grounded FAQ retrieval from document corpus
  • Semantic SQL generation for operational analytics
  • Real-time network diagnostics with tower data
  • Billing dispute resolution with audit trails
  • Professional customer communication generation
  • Fully traced agent execution for transparency

Prodapt operates as a regional telecom provider offering mobile voice, 4G LTE, and 5G data services across the United States to consumer, business, and enterprise customer segments. Solution Architecture Overview

The Prodapt AI Operations Center implements a multi-tier agent orchestration architecture where a LangGraph supervisor intelligently routes customer inquiries to specialized workers, each built on the most appropriate framework for that domain.

Interface Layer: Streamlit UI → Customer Query Input & Execution Trace Display
Orchestration Layer: LangGraph Supervisor with Structured Routing & State Management
Specialist Workers: PolicyRAG | NetworkAnalytics | NetworkDiagnosticsADK | BillingResolutionADK | CustomerCommsCrew
Retrieval Layer: LlamaIndex RAG (VectorStoreIndex) | LlamaIndex Semantic SQL (ObjectIndex)
Service Layer: Google ADK Agents (A2A Protocol) on Ports 8001 & 8002
Data Layer: SQLite Database (telecom_ops.db) with 9 core tables

Key Architectural Principles

  • No In-Memory Data: All operational data (towers, outages, billing, incidents) persists in SQLite with no Python dictionaries
  • Framework Specialization: Each framework handles exactly one domain for which it is optimized
  • Remote A2A Services: ADK agents expose domain logic as independent HTTP microservices
  • Transparent Orchestration: Every routing decision and tool call is captured in execution trace
  • Policy Compliance: All answers grounded in provided policy documents or live database queries

Database Architecture & Schema

All operational data is persisted in a normalized SQLite database following Prodapt's existing schema. No in-memory dictionaries or Python data structures store business data.

Core Tables

Table Name Purpose Used By
network_towers Tower inventory: region, city, technology (4G/5G), operational status Network Diagnostics ADK, Semantic SQL
tower_performance Performance metrics: latency, packet loss, throughput, signal strength, timestamp Network Diagnostics ADK, Semantic SQL
network_outages Historical outages: severity (CRITICAL/MAJOR/MINOR), duration, root cause, affected customers Semantic SQL Analytics, Policy RAG cross-reference
open_incidents Active NOC incidents linked to specific towers Network Diagnostics ADK tools
customer_subscriptions Active subscriptions: plan names, regional fees, account type Semantic SQL Analytics
billing_accounts Customer account state: current balance, account status Billing Resolution ADK lookup_billing_account tool
billing_charges Line items: amount, description, billing period, duplicate flag, invoice status (OPEN/PAID) Billing Resolution ADK check_duplicate_charges tool
billing_credits Applied or pending credits: amount, reason, status (APPLIED/PENDING_APPROVAL) Billing Resolution ADK apply_billing_credit tool
billing_disputes Dispute records: customer, charge, status (open/resolved), resolution Billing Resolution ADK audit trail

Data Flow Rules

  • Semantic SQL: Queries use only the most recent tower_performance sample (max recorded_at) per tower, not averages or historical data
  • Billing Accounts: current_balance = sum of all billing_charges where invoice_status='OPEN' minus all billing_credits where status='APPLIED'
  • Duplicate Detection: Same customer + same description + same billing period, OR is_duplicate_flag=1, OR cross-month plan repeats (not duplicates)
  • Credit Limits: Credits ≤ $50 are auto-applied (APPLIED status); credits > $50 require approval (PENDING_APPROVAL status)

Scenario 1: Policy & FAQ Resolution

Example Query
What is Prodapt's roaming policy for Western Europe? I have an Unlimited Plus plan.
Route: PolicyRAG → CustomerCommsCrew → FINISH

Execution Flow

  1. Supervisor Analysis: Identifies policy/FAQ intent from keywords ("roaming policy", "Europe", "plan details")
  2. PolicyRAG Worker: Invokes LlamaIndex VectorStoreIndex on roaming_policy.txt document corpus
  3. Retrieval: Vector embeddings match question to relevant policy sections (Zones A-D definitions, Travel Pass rates, plan inclusions)
  4. Synthesis: Query engine generates natural language answer grounded in roaming_policy.txt source
  5. Agent Context Update: PolicyRAG output added to conversation state: "Zone B includes Western Europe. Travel Pass: $10/day with 5GB. Unlimited Plus does not include Zone B roaming..."
  6. CrewAI Communications: Specialist drafts empathetic, policy-compliant response with cost breakdowns and options
  7. Quality Review: Secondary agent verifies tone, accuracy, and compliance before delivery
  8. Execution Trace Entry: Step 1: PolicyRAG → [policy excerpt], Step 2: CustomerCommsCrew → [final response]

Framework Rationale

LlamaIndex VectorStoreIndex excels at semantic document retrieval where the answer exists verbatim or can be synthesized from policy text. No SQL queries needed. RAG grounds answers in authoritative source documents, ensuring consistency and compliance.

Scenario 2: Network Analytics & Outage Trends

Example Query
Which region had the most CRITICAL network outages in the last 90 days? Can I get an SLA credit?
Route: NetworkAnalytics → CustomerCommsCrew → FINISH

Execution Flow

  1. Supervisor Analysis: Identifies analytics intent from keywords ("outage trends", "which region", "CRITICAL", "most")
  2. NetworkAnalytics Worker: Invokes LlamaIndex semantic SQL pipeline
  3. ObjectIndex Matching: Semantically matches question to network_outages table context string. ObjectIndex embedding finds best table match (network_outages vs tower_performance vs subscriptions)
  4. SQL Generation: SQLTableRetrieverQueryEngine generates: SELECT region, COUNT(*) FROM network_outages WHERE severity='CRITICAL' GROUP BY region ORDER BY COUNT DESC LIMIT 1
  5. Query Execution: Result: "Midwest region: 47 CRITICAL outages (45% of total)"
  6. Answer Synthesis: LlamaIndex generates natural language: "The Midwest experienced the highest concentration of CRITICAL outages with 47 incidents..."
  7. CrewAI Communications: Specialist cross-references with SLA policy, determines customer eligibility for Business/Enterprise tiers, calculates credit amounts
  8. Execution Trace: Step 1: NetworkAnalytics → [region stats], Step 2: CustomerCommsCrew → [eligibility determination + credit calculation]

Framework Rationale

LlamaIndex Semantic SQL automatically selects the correct table via vector embeddings without requiring users to write or understand SQL. SQLTableRetrieverQueryEngine handles the actual SQL generation and execution, making complex analytics accessible to non-technical staff.

Scenario 3: Network Diagnostics via ADK

Example Query
My 5G signal keeps dropping in Austin near tower TX-512. I get frequent disconnects. Please diagnose.
Route: NetworkDiagnosticsADK → CustomerCommsCrew → FINISH

Execution Flow

  1. Supervisor Analysis: Identifies network diagnostics intent from keywords ("signal drops", "tower ID", "diagnose", "5G")
  2. NetworkDiagnosticsADK Worker: LangGraph node invokes RemoteA2aAgent wrapper pointing to http://localhost:8001/.well-known/agent-card.json
  3. A2A HTTP Request: ADK runtime receives agent request via A2A protocol on port 8001
  4. ADK Tool Execution - check_tower_status(tower_id='TX-512'):
    • Queries: SELECT * FROM network_towers WHERE tower_id='TX-512'
    • Gets latest performance: SELECT * FROM tower_performance WHERE tower_id='TX-512' ORDER BY recorded_at DESC LIMIT 1
    • Joins open incidents: SELECT * FROM open_incidents WHERE tower_id='TX-512'
    • Returns: "Status: OPERATIONAL, Technology: 5G, Signal: -72 dBm, Packet Loss: 3.8%, Latency: 24ms, Open Incident: INC-8841"
  5. ADK Tool Execution - run_connectivity_diagnostics(tower_id='TX-512', symptom='frequent disconnects'):
    • Analyzes SQL data + incident history
    • Returns recommendations: "Packet loss within acceptable range. Incident INC-8841 reports fiber backhaul issues. Recommend NOC escalation."
  6. Response Collection: RemoteA2aAgent wrapper returns combined diagnostic report to LangGraph node
  7. CrewAI Communications: Specialist transforms technical findings into empathetic customer message with next steps

Why ADK?

Google ADK agents provide a structured agent framework with proper tool definition, streaming support, and the A2A protocol for remote service deployment. This allows Network Diagnostics to scale independently as a separate microservice.

Scenario 4: Billing Dispute Resolution via ADK

Example Query
Customer CUST-10002 was charged twice for Unlimited Plus ($65.99 × 2). Investigate and apply credit.
Route: BillingResolutionADK → CustomerCommsCrew → FINISH

Execution Flow

  1. Supervisor Analysis: Identifies billing intent from "CUST-" prefix, "charged twice", "credit"
  2. BillingResolutionADK Worker: LangGraph node invokes RemoteA2aAgent on port 8002
  3. ADK Tool 1 - lookup_billing_account(customer_id='CUST-10002'):
    • Query: SELECT * FROM billing_accounts WHERE customer_id='CUST-10002'
    • Returns current balance: $131.98
    • Query charges: SELECT * FROM billing_charges WHERE customer_id='CUST-10002' AND invoice_status='OPEN'
    • Returns: Two Unlimited Plus charges of $65.99 each (CHG-50021, CHG-50022)
  4. ADK Tool 2 - check_duplicate_charges(customer_id='CUST-10002'):
    • Detects: Same description ("Unlimited Plus"), same amount ($65.99), same billing period (September 2026)
    • Conclusion: Duplicate charge confirmed
    • Skips any charge already having APPLIED credit
  5. ADK Tool 3 - apply_billing_credit(customer_id='CUST-10002', amount=65.99, reason='Duplicate Unlimited Plus charge'):
    • Amount ($65.99) exceeds $50 auto-approval limit
    • INSERT into billing_credits: status='PENDING_APPROVAL' (awaits supervisor review)
    • current_balance remains $131.98 (no auto-deduction for pending credits)
    • Creates audit record with timestamp and reason
  6. Response: "Duplicate charge verified. Credit of $65.99 submitted for approval. You will be notified when processed."
  7. CrewAI Communications: Specialist drafts professional billing letter with next steps and timeline

Key Business Rules

Credit Amount Status Balance Impact
≤ $50.00 APPLIED Immediately reduced
> $50.00 PENDING_APPROVAL No change until approval

Scenario 5: Complex Multi-Worker Orchestration

Example Query
We experienced a 6-hour outage in the Midwest on September 12th. Multiple customers affected. Am I eligible for an SLA credit under Prodapt policy?
Route: NetworkAnalytics → PolicyRAG → CustomerCommsCrew → FINISH

Execution Flow

  1. Supervisor Analysis: Recognizes multi-domain question requiring both operational data AND policy interpretation
  2. First Worker - NetworkAnalytics:
    • ObjectIndex matches to network_outages table
    • Generates: SELECT * FROM network_outages WHERE region='Midwest' AND duration_hours >= 6 AND date='2026-09-12'
    • Result: "OUT-2026-0912: CRITICAL outage, 6 hours, 8,500 customers affected, fiber backhaul cut"
    • Agent context update: Operational facts captured
  3. Supervisor Re-evaluation: Now has outage facts; routes to PolicyRAG for eligibility determination
  4. Second Worker - PolicyRAG:
    • VectorStoreIndex queries sla_policy.txt
    • Retrieves: "Business Unlimited (6+ hours): $22.50/month credit. Enterprise Mobile (6+ hours): $62.25/month. Consumer: No credit."
    • Agent context update: Policy eligibility rules added
  5. Supervisor Decision: Both operational data and policy rules gathered; route to CrewAI for synthesis
  6. CrewAI Communications:
    • Specialist receives full agent_context: outage facts + policy rules
    • Drafts: "Your account qualifies for SLA credit. Business Unlimited customers receive $22.50 for the 6-hour Midwest outage. Credit will be applied within 2 business days."
    • Reviewer verifies accuracy of dollar amounts, eligibility, and compliance
  7. Execution Trace: Shows 3 steps in order: NetworkAnalytics → PolicyRAG → CustomerCommsCrew

LangGraph Supervisor Architecture

State Definition (AgentState)

class AgentState(TypedDict): messages: Annotated[list, add_messages] # Conversation history next: str # Supervisor routing decision user_query: str # Original customer inquiry agent_context: str # Accumulated worker outputs execution_trace: list[dict] # Step-by-step trace

Graph Structure

  • Start Node: Receives user query, initializes state
  • Supervisor Node: LLM with structured output determines next worker (PolicyRAG | NetworkAnalytics | NetworkDiagnosticsADK | BillingResolutionADK | CustomerCommsCrew | FINISH)
  • Worker Nodes (5 total):
    • PolicyRAG: Calls document_rag.py, updates agent_context
    • NetworkAnalytics: Calls sql_semantic_search.py, updates agent_context
    • NetworkDiagnosticsADK: Calls RemoteA2aAgent wrapper, updates agent_context
    • BillingResolutionADK: Calls RemoteA2aAgent wrapper, updates agent_context
    • CustomerCommsCrew: Calls CrewAI crew with full agent_context, produces final_response
  • Conditional Routing: Supervisor output routes to appropriate worker node or END
  • Loop Back: Each worker returns to supervisor (except CustomerCommsCrew, which triggers END)

Execution Trace Mechanism

Each worker node appends to execution_trace list after producing output:

execution_trace.append({ "worker": "PolicyRAG", "output": "Zone B includes Western Europe..." })

CrewAI final response is marked as the last trace entry before delivery to UI.
